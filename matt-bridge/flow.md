## Stages: who leads, what the person's skills add

| Stage | Leads | Artifact | The person's skills it hands to or reads |
| --- | --- | --- | --- |
| Idea | `grilling` (`grill-me`, `grill-with-docs`) | `GLOSSARY.md`, `docs/adr/NNNN-*.md` | decisions with the person, one question per message; ADRs land by PR |
| Spec | `to-spec` | parent issue | `roadmap-tracker`: milestone, pin if current feature |
| Tickets | `to-tickets` | child issues with `## Parent`, `## What to build`, `## Acceptance criteria`, `## Blocked by` | `roadmap-tracker`: milestone, state labels, blockers as real links; hot-file order |
| Build | `implement` with `tdd` | commits on a feature branch | `model-mix` before the launch; `git-conventions` for branch and commits; `clean-code`; `assertions-go-red` for assertions changed after the red |
| Build, many | `implement-spec` | integration branch, one worktree per implementer, a merger subagent | width and model per `model-mix`; `shared-machine-checks` when checks run here; one PR to main |
| Review | `code-review` (Standards, Spec) | report, posted as a PR comment | `clean-code` as a standards source; Opus high per `model-mix` |
| PR | `pr` | PR body | `git-conventions` title, `Closes #N`; mutation table in Evidence |
| Merge | `merge-gate` (nothing upstream) | one PR comment per round | reads the review comment, covers the rest; `coordinator-method` merge rule |
| Retro | `retro` | candidates, by severity | each accepted one: ticket via `roadmap-tracker`, or skill edit via `skill-audit` |
| Incoming issues | `triage` | labels, comments starting `> *This was generated by AI during triage.*`, `.out-of-scope/*.md` | queue and waiting lists (`roadmap-tracker` §5) |
| Bugs | `diagnosing-bugs` | red loop, failing test, `[DEBUG-xxxx]` log lines, fix | delegated thread; a stuck worker comes here before a second opinion |

Upstream `to-tickets` can also write a local tracker (`.scratch/<feature>/issues/NN-slug.md`). With a local tracker there is no `gh` milestone: tell the person the rule cannot apply and ask where the roadmap lives.

## Preface lines

One short message before invoking, not an edit of his text. Fill the brackets.

- Grilling: `Grill me one question per message: options, your recommendation, how many remain. Map the frontier first.`
- Spec: `After publishing, add milestone "[name]". Do not interview.`
- Tickets: `Publish HITL slices as [ready-for-human label]. I add the milestone after each issue. One question per message for the breakdown quiz. Hot files: [list]; propose a blocked-by edge between tickets that touch one.`
- Build: `Work on branch [feature/issue-N-slug], never main. Targeted tests only. No amend, no force.`
- Fan-out: `At most [N] implementers at once (N: one, or the Parallel cloud sessions number of today's model-mix profile when the budget is green and the slices are disjoint), each model [sonnet] effort [high]. The rest of the frontier waits. The merger touches the integration branch only; I merge to main.`
- Review: `Reviewers on model [opus] effort [high]. Report findings; do not merge. Post the report as a PR comment with the head sha.`

## Commands

Milestones and links are in `roadmap-tracker`. Used here:

```
gh issue edit N --milestone "<name>"
gh issue pin N
gh issue list --search "no:milestone" --state open
git branch --show-current
git grep "\[DEBUG-"
```

- `gh issue edit --milestone` takes the name. Whether it fails on an unknown or duplicate name is untested: create the milestone first.
- Pinning is limited to 3 issues per repo (GitHub docs). `gh issue pin` and `gh issue unpin` exist in gh 2.83.2.

## Unverified

- That `claude --cloud` workers cannot see `~/.claude/skills` (cloud-worker research, from the docs; check in the first session).
- That `implement-spec` honours a width given in its invocation. Its 1.3.1 text sets no width and asks for maximum concurrency, so the fan-out preface line is a local addition: watch the first run and stop it if it starts more implementers than the line allows.
